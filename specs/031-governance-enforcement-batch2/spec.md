## 1. Problema

La matriz de capacidades (t_d8ed9362) definió 29 policy keys nuevas; el catálogo tipado las combina (spec 029) y el endpoint las compila aplanadas en el bundle schema 2 (spec 019 REQ-GOH-024). El batch 1 (spec 030) cubrió las 8 keys de **configuración**. Este batch cubre las **21 keys de capacidad** — qué superficies funcionales puede tocar el agente (MCP, plugins, skills, memoria, secrets/vault, personalidad, voz, bot mode, hooks, cron, prompts recurrentes, goal mode, delegación, distribución de perfiles, retención de sesiones, checkpoints) — y cierra los gaps de enforcement E-1/E-2 y documenta E-3 en el threat model (ADR-018).

Regla transversal de la tarea: **deny-by-default** — si la key no está permitida en el bundle, la capacidad se veta con `BLOCKED by organization policy`, el veto se audita (log + conteo) y cuenta para la attestation.

## 2. Mecanismo (hereda spec 019, cero parches al core)

Módulo NUEVO del plugin `capability_enforcement.py`, cableado aditivamente desde `__init__.py::register(ctx)` bloque 6 (mismo patrón que `attestation.py`):

- **`pre_tool_call`** (veto duro): registrado DESPUÉS de los hooks de `enforcement` (spec 022) y `config_enforcement` (spec 030) — sus blocks ganan los empates (precedencia del core por orden de registro); este batch solo AÑADE vetos en modo normal. Si no hay bundle válido y la lane batch 1 no está cableada, este hook fail-closes por sí mismo (defensa en profundidad).
- **`post_tool_call`** (observador): cache handle→kind de `browser_vault action=list` para el veto de payment autofill (P-17).
- **`subagent_start`/`subagent_stop`**: contador de profundidad de delegación efectiva (P-12) — los children de `delegate_task` corren in-process y heredan el ejecutor con los hooks del proceso (E-1c).
- **`pre_gateway_dispatch`** (rewrite): los comandos de gateway gobernados (`/personality`, `/voice`, `/loop`, `/heartbeat`, `/goal`, `/subgoal`) se REESCRIBEN — el comando nunca ejecuta. Documentado fail-open del core (un hook que lanza se ignora): el hook es totalmente defensivo y el veto duro de esas capacidades vive donde el core es fail-closed (tools) o en el gate remoto.
- **`register_system_prompt_section`** (`after_memory`, id `trust-agent-personality-lock`): candado de personalidad cuando `allow_custom_personality=false` (P-14) — el SOUL.md queda POR DEBAJO de la policy (mandato Miller: la sección de gobernanza del núcleo v2 + la cláusula de precedencia por turno ya lo subordinan).
- **Pisos (P-27/P-28)**: `hermes sessions prune --older-than <N>d --yes --force` (primitiva oficial, 1 vez/24 h, hilo daemon) y overlay admin-pinned `checkpoints.enabled: true` en el managed scope (M16: el overlay GANA al config del usuario). Sin managed scope → desvío reportado, sin mutar el host.
- **Findings → attestation**: desvíos config-vs-policy y estado de pisos se persisten en `trust-agent/capability-findings.json` y viajan en el POST de attestation (campo `capability_findings`, canal aditivo retrocompatible: `AttestationBody.capability_findings: dict = Field(default_factory=dict)` en el control plane, payload de audit JSONB — sin migración).
- **Todo veto auditado**: `plugin.log` (`tool_vetoed`, `layer=capability`) + conteo en `trust-agent/veto-counts.json` (mismo contrato que `enforcement._count_veto`) → la attestation lo fusiona y reporta.
- **Keys resueltas SOLO vía `policy_contract.policy_value`** (REQ-GOH-023): key ausente (bundle schema 1) → default restrictivo del PLUGIN, nunca `payload.get()` crudo.

## 3. Decisiones de diseño (vinculantes)

| ID | Decisión | Razón |
|---|---|---|
| **D-031-01** | **P-6 `allowed_mcp_servers`**: veto POR NOMBRE de tool `mcp__<server>__*` en `pre_tool_call`. Las tools MCP son toolsets dinámicos; la ejecución directa pasa por el ejecutor común (`agent/tool_executor.py::_pre_tool_block`) → el veto por nombre alcanza: (a) tools MCP dinámicas, (c) los children de `delegate_task` (in-process, heredan el ejecutor), (d) el override `toolsets:` por ruta webhook (el override solo cambia qué tools se ANUNCIAN; la ejecución pasa por el mismo ejecutor con el mismo veto). E-1 queda CERRADO por construcción + unwrap. | Un solo choke point en el core cubre (a)/(c)/(d); el puente diferido requiere unwrap explícito porque el core lo excluye del hook (verificado en `agent/tool_executor.py`, cero parches). |

Desvío `agent.personalities` en config → finding. | Mandato Miller: la personalidad es voz; la policy es autoridad. |
| **D-031-07** | **P-21/P-22/P-9/P-10/P-11/P-25 entry points**: `allow_voice_mode` → `/voice` rewrite; `allow_bot_mode` → tool `message_agent` vetoada + desvío `agent.bot_mode_protocol` → finding; `allow_scheduled_tasks` → tool `cronjob_manage` vetoada + desvío `cron.allow_agent_scheduling` → finding; `allow_recurring_prompts` → `/loop`+`/heartbeat` rewrite; `allow_goal_mode` → `/goal`+`/subgoal` rewrite + `kanban_create(goal_mode=true)` vetoado por args; `allow_profile_distributions` → `terminal` con `hermes profile install`/`hermes import-agent` vetoado (entry point IN-PROCESS; el CLI directo del usuario es E-3b: control local). | Un entry point, un mecanismo: tool → veto duro; comando de gateway → rewrite; desvío de config → finding. |

**REQ-031-015** (M) [transversal] — Toda key de este batch se resuelve vía `policy_contract.policy_value` (deny-by-default por key ausente, REQ-GOH-023); un bundle schema 1 (sin las keys) deja las capacidades vetadas con los defaults restrictivos del plugin. Cero parches al core: solo `ctx.register_*` + I/O local de config.yaml del perfil (sin imports de `hermes_cli`).
> **AC-031-015**: (unit) payload sin las keys → vetos con defaults restrictivos (vault false, depth 0, skills `[]`…); el test de cero parches (AC-GOH-016) sigue pasando.

## 5. Amenazas y límites (hereda D-GOH-07)

El enforcement local de este batch es defensa en profundidad: un usuario del SO puede deshabilitar el plugin o editar su config. Las garantías duras siguen siendo remotas (LiteLLM, vault server-side, revocación) y la detección es por attestation (ausencia = señal). Los residuales específicos de este batch (E-3a/b/c) quedan en la spec 019 §6 — esta spec no promete imposibilidad de bypass local.
