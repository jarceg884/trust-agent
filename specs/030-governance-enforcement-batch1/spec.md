## 1. Problema

La matriz de capacidades (t_d8ed9362) inventarió 62 capacidades de Hermes y definió 29 policy keys nuevas (P-1..P-29). El catálogo tipado ya las combina (spec 029, migración `0022_policy_catalog_v2`) y el endpoint del bundle las compila DINÁMICAMENTE (spec 019 REQ-GOH-024, schema 2). Lo que falta es el **enforcement en el plugin**: que el agente Hermes del dispositivo haga caso a esas keys POR ENCIMA de su `config.yaml` local (managed scope como vehículo, ADR-016).

Este batch cubre las **8 keys de configuración** del agente; el batch 2 (t_a868974a) cubre las keys de capability (MCP, plugins, skills, memoria, secrets, vault, personality, voice, bot-mode, hooks, cron, delegación, retención, checkpoints, profile distributions) y los gaps E-1..E-3.

## 2. Mecanismo (hereda spec 019, cero parches al core)

Módulo NUEVO del plugin `config_enforcement.py`, cableado aditivamente desde `__init__.py::register(ctx)` (mismo patrón que `attestation.py`):

- **`pre_tool_call`** (veto duro): se registra DESPUÉS del hook de `enforcement.py` (spec 022). Si el modo operativo es `restricted`, el hook retorna `None` — `enforcement` ya bloqueó todo (fail-closed heredado, REQ-GOH-009/010); en modo `normal` aplica los checks de este batch. Precedencia del core: `block` > `approve`; con dos blocks gana el primero en orden de registro (el de `allowed_tools`/restricted de spec 022).
- **`pre_llm_call`** (contexto por turno): nota de violación de `approval_mode` + mensaje de policy de `allowed_providers` (el hook NO puede vetar la llamada — D-HRB-08; el gate duro de modelos es LiteLLM, defensa en profundidad) + disparo del sync de config administrada.
- **Config local leída de `$HERMES_HOME/config.yaml`** (parse YAML con caché por mtime): el plugin NO modifica el comportamiento del core — lo **veta por encima** cuando la config local contradice la policy firmada.
- **Managed scope como vehículo (ADR-016, E-3)**: además del veto, el plugin **sincroniza** las secciones de `security.*` que la policy gobierna (`website_blocklist`, `allow_private_urls`, `allow_lazy_installs`) directamente en `config.yaml` — escritura atómica idempotente que SOLO impone restricciones (jamás relaja ni resetea): el mecanismo nativo M11/M10 de Hermes las hace cumplir con su propia maquinaria (TTL de recarga corto, verificado en `tools/website_policy.py`), y el veto del plugin queda como defensa en profundidad.
- **Todo veto auditado**: `plugin.log` (`tool_vetoed`, `layer=config_batch1`) + conteo en `trust-agent/veto-counts.json` (mismo esquema que `enforcement._count_veto`) → la próxima attestation (spec 019 Inc. 3) lo fusiona y reporta (`veto_counts`/`escalated_tools` en `device.attestation`).
- **Keys resueltas SOLO vía `policy_contract.policy_value`** (REQ-GOH-023): key ausente (bundle schema 1) → default restrictivo del PLUGIN, nunca `payload.get()` crudo.

## 3. Decisiones de diseño (vinculantes)

| ID | Decisión | Razón |
|---|---|---|
| **D-030-01** | `approval_mode`: el plugin NO puede re-activar el gate de aprobaciones del core (no existe API de plugin para ello). El veto es: mientras el modo efectivo esté POR DEBAJO del piso de policy, las tools de ejecución (`terminal`, `process_manage`, `execute_code`, `computer_use`) quedan bloqueadas con mensaje de policy. El estado se **re-evalúa en CADA llamada** (cubre `/yolo` persistido por sesión, `--yolo`/`HERMES_YOLO_MODE` congelado a nivel proceso y `approvals.mode` de config). | El bypass real de YOLO vive en la superficie de ejecución; bloquearla restaura el efecto del piso sin parchear el core. |
| **D-030-02** | Modo efectivo de aprobación, en orden: (1) `HERMES_YOLO_MODE` truthy → `off`; (2) `tools.approval._YOLO_MODE_FROZEN` (import puntual y lazy del core, solo lectura) → `off`; (3) `/yolo` de sesión: `tools.approval.is_session_yolo_enabled(session_id)` (el hook recibe `session_id` — verificado en `hermes_cli/plugins.py::_get_pre_tool_call_directive_details`) → `off`; (4) `approvals.mode` de config (default `smart` si ausente). Rank: `manual`(2) > `smart`(1) > `off`(0) — mismo `STRING_RANKS` del combinator (spec 029). | Cuatro superficies reales del bypass, citadas en la matriz C-003/P-1. |
| **D-030-03** | `require_write_sandbox`: raíces permitidas = `HERMES_WRITE_SAFE_ROOT` (mecanismo nativo, `os.pathsep`-separado) si está seteado; si no, **el cwd del proceso** (el workspace de la sesión). `write_file`/`patch` con path resuelto fuera de las raíces → veto. `$HERMES_HOME` NO es raíz: el agente no debe editar su propia config/SOUL con tools de escritura (E-3). | "Workspace del dispositivo" = el árbol donde corre la sesión; el env nativo es el vehículo administrado por la org. |
| **D-030-04** | `allowed_env_passthrough`: superficie validada = (a) asignaciones `NAME=value` en posición de comando (inicio de segmento, tras `;`/`&&`/`\|\|`/`\|`/`(`/`sudo `/`env `) y `export NAME=`, en `command`/`code`; (b) `terminal.env_passthrough` y `terminal.docker_forward_env` de config. Cualquier nombre fuera de la allowlist (`*` = todos) → veto. Las `required_environment_variables` de skills son piso del batch 2 (`allowed_skills`); aquí se documenta que la declaration se valida cuando su env cruza la superficie terminal. | El hook ve el comando y la config, no el env final del child (M10 del core ya hace scrubbing de secretos: esta capa es la policy de la org encima). |
| **D-030-05** | `web_domain_policy`: (a) **allowlist** — toda tool con URL en args (`web_extract`, `vision_analyze`, `browser_*`, y `command`/`code` de terminal/execute_code) debe apuntar SOLO a dominios de la lista (match exacto o subdominio); `web_search` solo pasa si el query restringe con `site:<dominio-allowlisted>` o menciona un dominio de la lista; (b) **blocklist** — dominio en la lista → veto + **sync administrado** de `security.website_blocklist` en config.yaml (el mecanismo nativo M11 también lo aplica); (c) **open** — sin veto de dominios. El sync administrado SOLO impone (blocklist con dominios / `allow_private_urls: false` / `allow_lazy_installs: false`), nunca resetea una restricción previa (una blocklist stale es MÁS restrictiva: dirección fail-closed). | El modo allowlist no existe en el core nativo → veto del plugin; el blocklist sí → ambas capas. |
| **D-030-06** | `allow_private_network_access=false` (default restrictivo): veto de tools con URL a hosts privados — IPs literales (RFC1918, loopback, link-local, reserved, multicast, IPv6 ULA), `localhost`/`.localhost`/`.local`/`.internal`. Hostnames con DNS interno no resolvibles sin red quedan para el gate nativo (`allow_private_urls: false` forzado por sync administrado — el core resuelve y aplica). | El plugin no hace DNS en el hot path (latencia + red por tool call); literales + localhost son el 99% del SSRF de agente; el nativo cubre la resolución. |
| **D-030-07** | `allowed_providers`: el hook `pre_llm_call` calcula el conjunto de providers efectivos de config (`model.provider`, `fallback_providers`, `provider_routing.only/sort/order`, providers de `auxiliary.*`, `local_runtime`, presets MoA) y, si alguno cae fuera de la lista (`*` = todos), inyecta el mensaje de policy por turno + cuenta el veto para attestation. Clasificación: provider `custom`/`openai-compatible` con `base_url` se clasifica `litellm_gateway` (contrato del profile template: base_url = gateway del tenant). **Residual documentado (D-GOH-07)**: repuntar `base_url` a un proxy personal no es distinguible localmente — el gate duro es LiteLLM (la virtual key solo vive en el gateway de la org) y la detección es remota. | `pre_llm_call` es hook de contexto (no veta — D-HRB-08); el mensaje de policy al usuario + el conteo para attestation son el entregable del plugin, el piso duro es el gate remoto (defensa en profundidad, mandato de la tarea). |
| **D-030-08** | `allow_self_updates=false` (default restrictivo): veto de `terminal`/`process_manage`/`execute_code` cuyo comando/código invoque self-updates: `hermes update`, `hermes plugin(s) install|add|enable`, `pip`/`uv`/`uvx` instalando paquetes `hermes*`; + sync administrado que fuerza `security.allow_lazy_installs: false` (los lazy installs del core quedan desactivados). | C-045: las tres superficies de auto-modificación del agente. |
| **D-030-09** | Lectura del estado del core (`tools.approval`) por import lazy y puntual, solo lectura, con `try/except` — el plugin funciona sin el core presente (tests standalone). El test automatizado de cero parches (AC-GOH-016) sigue pasando: sin imports de `hermes_cli`, sin escrituras a archivos del core; la única escritura fuera del plugin es el sync administrado de `security.*` en el `config.yaml` del perfil (vehículo documentado). | Importar para LEER no es parchear; el grep de AC-GOH-016 cubre `hermes_cli`. |
| **D-030-10** (hallazgo live, enmienda de D-030-09) | **Home context-aware**: `enroll.hermes_home()` y `bundle_client.hermes_home()` resuelven vía `hermes_constants.get_hermes_home()` (override context-local → `HERMES_HOME` → default), NO env-first. En el modelo un-gateway-por-host el gateway multiplexor ejecuta las tools de las sesiones de VARIOS perfiles: su env `HERMES_HOME` es el home del gateway y el override context-local (`set_hermes_home_override`, `gateway/run.py`) es el que apunta al perfil servido. Leer env-first hacía que la instancia del plugin en el gateway no encontrara el device token del perfil → modo restringido espurio (vetos fail-closed en lugar de vetos de policy). Fallback a env/default solo sin `hermes_constants` (tests standalone). | Hallazgo de la evidencia live: los vetos llegaban con mensaje "restricted mode (device not enrolled)" desde el pid del gateway, no desde la sesión. |
| **D-030-11** (hallazgo live) | `hermes -z` fuerza `HERMES_YOLO_MODE=1` en TODA sesión one-shot (`hermes_cli/oneshot.py`: "Non-interactive by definition") → el modo efectivo de aprobación de toda sesión `-z` es `off`. Consecuencias: (a) el veto P-1 dispara en CUALQUIER sesión -z con piso smart/manual — la superficie de ejecución queda vetada a menos que la policy lo permita; (b) la evidencia live aísla las keys usando fases con `approval_mode=off` (A/B) y demuestra P-1 con piso `manual` (C). | Comportamiento del core verificado en fuente; el plugin lo trata como una superficie más del bypass (D-030-02 superficie 1). |
| **D-030-12** (hallazgo live) | El gateway cachea el plugin manager por perfil y retiene el código viejo del plugin en memoria. Toda sincronización de código del plugin al perfil para evidencia/deploy debe acompañarse del nudge `reload-plugins` por control socket (`gateway.control_socket.reload_gateway_plugins(root, profile_home=...)`) para que la instancia del gateway evalúe con el código nuevo. | Sin el nudge, las sesiones son evaluadas por la instancia anterior (con el bug de home) aunque el dir del perfil tenga el código nuevo. |

## 4. Requisitos (formato EARS)

Trazabilidad: serie **REQ-030**. Padre: spec 019 (REQ-GOH-005..012, D-GOH-11), matriz §3.

**REQ-030-001** (M) [P-1, D-030-01/02] — Cuando el agente opera con un modo de aprobación efectivo cuyo rank es inferior al piso `approval_mode` del bundle vigente, el hook `pre_tool_call` bloquea las tools de ejecución (`terminal`, `process_manage`, `execute_code`, `computer_use`) con mensaje `BLOCKED by organization policy: approval mode '<efectivo>' is below the organization floor '<piso>'...`, re-evaluado en cada llamada (un `/yolo off` restaura al vuelo), y el veto queda auditado (log + conteo attestation).
> **AC-030-001**: (unit) con policy `manual` y config `approvals.mode: off` → `terminal` bloqueada con el mensaje; con `HERMES_YOLO_MODE=1` → bloqueada; con `/yolo` de sesión activo (fake del core) → bloqueada y tras desactivarlo → el veto de approval_mode no dispara; con policy `off` y config `smart` → no dispara. (live) sesión real con `HERMES_YOLO_MODE=1` y policy `manual` → `terminal` bloqueada con el mensaje de policy en la sesión.

**REQ-030-002** (M) [P-2] — Cuando el backend de terminal efectivo (`terminal.backend` de config, default `local`) no está en `allowed_terminal_backends` del bundle (`*` = todos), el plugin bloquea `terminal` y `process_manage` con mensaje de policy. El plugin NO cambia el backend: lo veta.
> **AC-030-002**: (unit) policy `["docker"]` + config `local` → bloqueada con mensaje; policy `["*"]` → no dispara. (live) sesión real con policy `["docker"]` → `terminal` bloqueada con el mensaje.

**REQ-030-003** (M) [P-5, D-030-03] — Cuando `require_write_sandbox` es true, `write_file`/`patch` con path resuelto fuera de las raíces sandbox (`HERMES_WRITE_SAFE_ROOT` o cwd) queda bloqueado con mensaje de policy; dentro de las raíces procede (además del denylist nativo de Hermes, que sigue aplicando).
> **AC-030-003**: (unit) `HERMES_WRITE_SAFE_ROOT=$tmp/root` → write a `/etc/x` bloqueado, write a `$tmp/root/a.txt` pasa; sin env → write fuera de cwd bloqueado. (live) sesión real → `write_file` a `/tmp/batch1-*.txt` bloqueado con el mensaje.

**REQ-030-004** (M) [P-18, D-030-04] — Cuando una llamada a `terminal`/`execute_code` llevaría al child variables de entorno no incluidas en `allowed_env_passthrough` (asignaciones explícitas del comando o passthrough configurado), el plugin la bloquea con mensaje de policy nombrando las vars ofensoras.
> **AC-030-004**: (unit) policy `[]` + comando `SECRET_TOKEN=x echo hi` → bloqueada nombrando `SECRET_TOKEN`; comando `echo foo=bar` (posición de argumento) → no dispara; config `terminal.env_passthrough: [SECRET_X]` + policy `[]` → bloqueada; policy `["*"]` → no dispara. (live) sesión real con policy `[]` → comando con `TRUST_SECRET_X=1` bloqueado con el mensaje.

**REQ-030-005** (M) [P-19, D-030-05] — Cuando `web_domain_policy.mode=allowlist`, toda tool con URL debe apuntar a dominios de la lista y `web_search` debe restringir con `site:`; cuando `mode=blocklist`, los dominios de la lista quedan vetados y el plugin sincroniza `security.website_blocklist` en `config.yaml` (managed scope) para que el mecanismo nativo M11 también lo aplique.
> **AC-030-005**: (unit) allowlist `["example.org"]`: `web_extract` a `evil.com` → bloqueada; a `sub.example.org` → pasa; `web_search "site:example.org q"` → pasa; `web_search "q"` → bloqueada; blocklist: `evil.com` bloqueada + `config.yaml` gana `security.website_blocklist.enabled=true, domains=[evil.com]` preservando el resto del archivo, idempotente. (live) sesión real con allowlist `["example.org"]` → `web_extract` a `http://127.0.0.1:8000/health` bloqueada con el mensaje.

**REQ-030-006** (M) [P-20, D-030-06] — Cuando `allow_private_network_access=false`, toda tool con URL a un host privado (IP literal privada/loopback/link-local/reserved, `localhost`, `.local`, `.internal`) queda bloqueada con mensaje de policy, y el sync administrado fuerza `security.allow_private_urls: false` en `config.yaml`.
> **AC-030-006**: (unit) `web_extract http://10.0.0.1/x` y `http://localhost/x` → bloqueadas; `http://8.8.8.8/x` → no dispara (modo open); config gana `allow_private_urls: false`. (live) cubierto por AC-030-005 live (127.0.0.1 dispara private-net en el mensaje).

**REQ-030-007** (M) [P-26, D-030-07] — Cuando el conjunto de providers efectivos de la config local cae fuera de `allowed_providers`, el hook `pre_llm_call` inyecta por turno el mensaje `BLOCKED by organization policy: provider '<x>' is not allowed...` y el veto queda contado para la próxima attestation; el gate duro de modelos sigue siendo LiteLLM (defensa en profundidad).
> **AC-030-007**: (unit) config con `fallback_providers: [anthropic]` + policy `["litellm_gateway"]` → el contexto del turno contiene el mensaje con `anthropic` y el conteo registra el veto; config `provider: custom` + `base_url` → clasificado `litellm_gateway` → sin mensaje (sin falso positivo contra el perfil gobernado real). (live) la sesión real del perfil enrolado (custom→gateway) corre SIN mensaje de provider (control negativo).

**REQ-030-008** (M) [P-29, D-030-08] — Cuando `allow_self_updates=false`, el plugin bloquea las llamadas cuyo comando/código invoque `hermes update`, `hermes plugin(s) install|add|enable` o installs de paquetes `hermes*` vía pip/uv, y el sync administrado fuerza `security.allow_lazy_installs: false`.
> **AC-030-008**: (unit) `hermes update` y `hermes plugin install foo` → bloqueados con mensaje; `ls -la` → no dispara; config gana `allow_lazy_installs: false`. (live) sesión real → `hermes update` por terminal bloqueado con el mensaje.

**REQ-030-009** (M) [spec 019 REQ-GOH-012/017] — Cuando este batch veta una llamada, el veto queda en `plugin.log` (`tool_vetoed`, con `layer=config_batch1` y el reason) y suma al conteo por tool en `veto-counts.json`, que la próxima attestation fusiona y reporta al control plane.
> **AC-030-009**: (unit) tras N vetos, `veto-counts.json` contiene los conteos y `plugin.log` las filas `tool_vetoed`. (live) tras la sesión, `plugin.log` del perfil muestra los vetos con `layer=config_batch1`.

**REQ-030-010** (M) [Constitution IV, spec 019 REQ-GOH-016/023] — Toda key se resuelve vía `policy_contract.policy_value` (key ausente → default restrictivo del plugin); el módulo no importa `hermes_cli` ni escribe archivos del core; en modo restringido (offline/desligado) este batch no añade nada (el fail-closed de spec 019/022 ya bloquea todo).
> **AC-030-010**: (unit) bundle schema 1 sin keys del batch → `terminal` bloqueada (allowed_terminal_backends ausente = `[]`), write sandbox exigido, approval floor `manual`; el test automatizado de AC-GOH-016 (grep de imports de `hermes_cli`) sigue pasando con el módulo nuevo.
